AI setup basics

The minimum you need to know about llm.json to get AI-driven villagers running. For the full operator-level reference, see docs/llm-providers.md — this page only covers "get it working."

You don't need this to play at all

promptworld runs perfectly well with no AI configured — villagers just act on simple built-in behavior instead of model-driven decisions ("reflex-only"). If you delete or never set up llm.json, that's exactly what you get: a working, watchable village, just without the AI layer described on the previous page.

Where the configuration lives

promptworld new automatically writes an llm.json file into your world's save directory with sensible defaults already filled in — you don't have to write one from scratch. It's read once, when the daemon starts; if you edit it, restart the world for the change to take effect:

promptworld stop demo
promptworld start demo

The easiest path: a local model

For everyday villager decisions, promptworld expects an OpenAI-compatible model server running on your own machine — Ollama is the common choice, listening at http://localhost:11434/v1 by default. A freshly created world's llm.json already names cogito:3b as that model — the one proven, across long test runs, to actually cooperate with the game's tool-calling out of the box, so there's nothing to reconfigure to make it work. Install Ollama, then pull the model:

ollama pull cogito:3b

promptworld new prints this exact command for you as part of its "world created" summary, so you never have to guess which model name to use — it's read straight from the same defaults the world was just written with.

Optional: the cloud tier

A handful of higher-value moments — nightly memory digestion, the narrated chronicle, and the guardian's own conversation with you — are worth spending on a higher-quality cloud model instead of the local one. To enable that tier, set an ANTHROPIC_API_KEY environment variable before starting the daemon; the key itself is never written into llm.json, only the name of the environment variable that holds it. Skip this and those moments simply don't run — nothing else breaks.

The default llm.json also wires up one more, much smaller kind of call: a cheap yes/no check the guardian uses to confirm a loosely-phrased standing order ("when Rowan seems heartbroken") really matches before acting on it. It tries the local model first and falls back to cloud, and needs no setup beyond what's already above. If you're carrying forward an older world's llm.json from before this existed, promptworld fills in that default for you automatically the next time the world starts, with one line in the startup log noting it did so.

Optional: memory embeddings

There's one more optional, off-by-default piece: a small local model that gives every villager memory a "meaning fingerprint," the groundwork for a smarter memory-recall feature that's still being evaluated (see the AI behind the village for what that feature actually does for players). Leave it out and nothing about your village changes. To turn it on, pull the model:

ollama pull all-minilm

then add it to llm.json as its own provider on the embedding route:

"providers": {
  "embedder": { "transport": "openai_compat",
                "endpoint": "http://localhost:11434/v1",
                "model": "all-minilm:latest" }
},
"routes": {
  "embedding": ["embedder"]
}

Prefer the full all-minilm:latest name exactly as shown over a shortened version — a shortened name still works for the model itself, but it briefly trips a spurious warning at startup (the warning clears by itself the first time a memory is fingerprinted; the full name avoids even that blip). This only adds the fingerprinting; the separate switch that actually changes which memory a villager recalls stays off until that feature clears its own evidence review. Full detail (and the evidence-review switch itself) lives in docs/llm-providers.md.

Checking it's actually working

  • promptworld status demo (and the systems tab in the full-screen client) shows you, per configured model, whether it's up, how busy it is, and how much you've spent this month.
  • promptworld llm demo planner "..." fires one test call directly and tells you which model actually answered.
  • promptworld calibrate demo benchmarks your setup and tells you which game speeds are safe to run at with your hardware and model choice — worth running once after any setup change. It measures one response at a time, so it prints a reminder that a real, busy village asking the same model for many things at once will run somewhat slower than the number it reports — the number is a floor, and the world adjusts its own sense of pace upward as it actually runs.

A world you've never calibrated isn't broken — it just runs on cautious built-in guesses instead of a measured pace, and says so with a one-time warning the first time you start it. promptworld status also lists, per configured AI provider, either the date you last ran calibrate on it or uncalibrated (bootstrap) if you haven't yet, so you can always tell at a glance.

You shouldn't even need to go looking, though: promptworld watches its own model connection and speaks up the moment something's actually wrong. If the model named in llm.json isn't there, or its server can't be reached, or it's a model that never uses "tool calling" the way the game needs, you'll see a WARNING line in status naming the problem and what to do about it, plus a red badge in the full-screen client's header — checked right at startup and again periodically while the problem lasts. Fix it, and the warning clears on its own; nothing to restart.

If something looks broken

If villagers seem to be getting stuck or the log shows a run of malformed responses, some smaller local models are unreliable at the structured "tool calling" promptworld's AI-driven decisions rely on — the same condition the automatic warning above is watching for. There's a per-model fallback setting for exactly this case (the warning's own suggested fix, when it applies), covered along with everything else past this "get it working" level — multiple models, custom routing, spending limits, and upgrading an older configuration — in the full operator reference: docs/llm-providers.md. This page intentionally stops here; that guide is where the deeper knobs live.
