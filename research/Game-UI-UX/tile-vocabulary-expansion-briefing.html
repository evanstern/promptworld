Expanding the tile vocabulary

What the corpus supports for new tile types, alternative colors, avatar characters, and fonts — rendered from Analysis-Tile-Vocabulary-Expansion.md.

Verdict — expand by borrowing conventions, not by inventing. Spend color before spending new characters; treat the roguelike/CP437 vocabulary as the dictionary for new tiles; keep avatars as case-coded letters and push emoji to the inspector layer; and if a richer surface is wanted, ship it as a swappable "tileset" skin over the same grid — never a second rendering model.

The vocabulary being expanded

Everything below is shipped today (internal/tui/views.go:1581–1644 and the tile switch at 1290–1330). Three properties make this baseline corpus-correct, and every addition must preserve them: it uses the shared convention where one exists, it distinguishes states by style rather than new glyphs, and one shared table feeds both the legend and the ? overlay.

The four rules of the verdict

RULE 1

Borrow, don't invent

New terrain comes from the roguelike convention set, then CP437. A novel glyph is a vocabulary word the player must learn — Ge: "many players have difficulty making that conceptual leap."

RULE 2

Color before characters

A new state of an existing thing is a style variant of the learned glyph — the cold-fire / dying-fire / damaged-wall pattern — never a new character.

RULE 3

Letters on the grid, emoji in the inspector

Case-coded initials carry two free channels (who + awake/asleep). Smallville's emoji ambience belongs to the strip/roster layer, not terminal cells.

RULE 4

One grid, swappable skins

DF Classic ↔ Premium is "just swapping out some glyphs. The grid structure underneath is the same everywhere." Any richer tileset is a projection of the same tile table.

New tile types — the selection ladder

ASCII maps read fast because players leverage "years of experience distinguishing a very specific set of symbols" (Ge, ASCII vs. Tiles). That advantage only accrues to conventional glyphs, so candidates are taken in this order:

Novel Unicode — last resort

The project has gone here before (ᴥ ▣ ✝) and it works because each is visually unlike everything else on the grid. Alternative colors — a semantic grammar, not a decorative one

Severity is a fixed 4-step language

RimWorld codes every event with the same four colors, on letters and on its History graph. Any new promptworld color should first answer "which severity band is this?"

◆goodblue
◆neutralgrey
◆badyellow
◆direct threatred

States recolor; they never re-glyph

The shipped dimming/warning grammar, generalized: faint = spent, warm-shift = deteriorating, bold+underline = critical. RimWorld 1.5's mood glow is the same move.

one glyph, many states ▲ lit ▲ dying ▲ cold ▤ intact ▤ damaged A fine A critical a suppressed

Where each palette lives

  • Meaning-bearing colors → the themeable ANSI 16. Danger, severity, faction. User themes then can't break semantics (terminals expose 16 user-themeable colors — Textual).
  • Material colors → the 256 palette. The earth tones (130/136/137/166/178/202/208) are decorative distinctions, not warnings. Cost: they ignore user themes and can collapse on 16-color terminals.
  • Externalize the scheme. Cogmind keeps message colors in an external text file explicitly as a colorblind aid — promptworld's ratified skin-token contract (D2) is the same mechanism. New tile colors are born as tokens, never literals.
  • Never color alone. Cogmind's multi-channel rule + WCAG H86: anything a player must act on needs a second channel — glyph, case, legend, or a feed line. Path-vs-grass is tolerable only because it's low-stakes.

Avatar characters — letters on the grid, emoji one layer up

The corpus offers three avatar models: DF/roguelike letters, RimWorld's portrait bar, and Smallville's sprites with LLM-generated emoji speech bubbles. Per-agent inspection is documented to hold to ~25 agents; promptworld's 8–20 villagers sit inside that. Keep initials as grid identity — and steal the Smallville chain at the strip/inspector layer, where the TUI's roster → detail drill-down already mirrors it:

Emoji as map glyphs are a layout hazard in a terminal: double-width characters break cell alignment (inferred from the corpus's cell-geometry facts, not a documented failure — see open questions). On a web renderer, over-avatar bubbles are proven by Smallville and could coexist with letter glyphs — the rule is renderer-specific.

Fonts — an architecture decision, three grounded rules

FONT 1

Mixed dimensions are the ideal

Cogmind: square-ish cells for the map, narrow fonts for text panels — "the best of both worlds." The TUI already fakes square cells by writing a space after every tile; a web renderer should make it explicit: the map font and the UI font are two choices.

FONT 2

CP437 coverage is the gate

Any candidate must cover box-drawing, shading, and the shipped set (⌂ ▣ ▤ ▩ ♠ ᴥ ✝) at map size. The corpus names requirements, not fonts — a known gap.

FONT 3

Scale cell size, never grid extent

Cogmind fixes a guaranteed-visible map area and balances gameplay against it; font size is the responsive variable. Don't let a font choice silently change how much world a player sees.

If "expand tiles" means a graphical tileset

One grid model, swappable glyph/tile skins. DF Classic and Premium are one codebase — "the switch… is just swapping out some glyphs. The grid structure underneath is the same everywhere" (Tarn Adams). ASCII glyphs and any sprite tileset are projections of the same tile table — which also matches the one-legend-source discipline and the skin-token direction.

Both halves of the DF evidence apply: Ge's market fact that "the average player will always choose to play with a tileset" argues for shipping one; DF Premium's documented visual noise in busy forts is the caution — richer tiles raise the noise floor, and Sylvester's "noise is signal that fails to transmit meaning" applies to tile art exactly as to text.

Tensions & open gaps

Convention vs. fiction. The roguelike dictionary carries meanings from other games. If promptworld's audience is less genre-literate than Cogmind's, the "pre-learned" advantage weakens — the legend/?-overlay channel has to carry more.

Earth tones vs. themeability. The 256-palette materials are what make the map read warm and physical, but they forfeit theme-consistency. "Semantics on the 16, materials on the 256" preserves both at a real cost the skin-token layer only partially recovers.

  • No specific font names are grounded — only coverage and dimension requirements. A small follow-up research pass would close this before a web renderer commits.
  • No tested colorblind-safe palette exists in the branch. Cogmind externalizes colors for colorblind players and RimWorld's severity language is hue-dependent, but neither source supplies a validated palette. The skin-token contract is the home; the palette itself is ungrounded.
  • Natural-language state at density (the MOC's standing open question) bears directly on the avatar/emoji layer and remains unresearched.
